### ✓ Evidence-Backed Compliance Findings

#### **FINDING 1: Resume Failure Error Code Mismatch (MEDIUM SEVERITY)**

**File:line:** `omnigent/server/routes/sessions/routes_lifecycle.py:409`

**Spec Requirement (line 46):** *"Resume acquisition/reconstruction/bind failure | Best-effort cleanup of the newly acquired claim. Atomically restore/retain detached state; `503 RESUME_FAILED`."*

**Spec Requirement (line 45):** *"Resume target removed/full/unavailable | Sanitized actionable `409 SANDBOX_UNAVAILABLE`"*

**Issue:** The code returns `409` for all resume failures including acquisition/reconstruction/bind failures that should return `503 RESUME_FAILED`:

```python
except Exception as exc:
    # ... cleanup ...
    raise HTTPException(
        status_code=409,  # Should be 503 for reconstruction/bind failures
        detail="Selected sandbox is unavailable; the session remains detached",
    ) from exc
```

**Impact:** Clients cannot distinguish between "target unavailable" (409) and "acquisition/reconstruction failure" (503), violating the spec's requirement for distinct error codes. Error message says "sandbox unavailable" but covers acquisition failures too.

**Reproduction:** Call `POST /v1/sessions/{id}/resume` where the sandbox app is available but repository reconstruction fails (e.g., git clone failure). The response will be `409` instead of `503`.

**Test confirms issue:** `test_resume_failure_leaves_session_detached_and_redacts_provider_error` expects `409` but spec requires `503` for this failure class.

#### **FINDING 2: Error Message Accuracy (LOW SEVERITY)**

**File:line:** `omnigent/server/routes/sessions/routes_lifecycle.py:409`

**Issue:** Error message "Selected sandbox is unavailable" is inaccurate when failure is due to acquisition/reconstruction (git clone, etc.) rather than target unavailability.

**Impact:** Misleading guidance to operators about failure root cause.
